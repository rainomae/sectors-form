# Sectors form

A small full-stack application that replaces the static `index.html` form fragment with a working
web form: a person enters their name, picks the sectors they are involved in from a hierarchical
list, agrees to the terms and saves. The data is stored in PostgreSQL, refilled into the form and
stays editable by the same person for the duration of their browser session.

| Part | Stack |
|---|---|
| Backend | Java 25, Spring Boot 4.1, Gradle (Groovy DSL), Spring Data JPA, Flyway, PostgreSQL, H2 in tests, springdoc-openapi, Spotless, JaCoCo |
| Frontend | React 19, TypeScript, Vite |
| Tests | JUnit 5 + MockMvc integration tests, Vitest unit tests, Playwright end-to-end tests |
| Runtime | Docker Compose (PostgreSQL, backend, nginx-served frontend) |

Repository layout (parts marked *planned* arrive in later steps):

```
sectors-form/
├── backend/            Spring Boot application
│   └── tools/          generator for the sector seed migration
├── docs/original/      the index.html the task started from
├── frontend/           React + TypeScript + Vite application
├── docker-compose.yml  PostgreSQL (backend and frontend services are added in step 7)
└── README.md
```

## 1. The task

The original brief, verbatim:

> 1. Correct all deficiencies in index.html
> 2. "Sectors" selectbox:
>    2.1 Add all the entries from the "Sectors" selectbox to database
>    2.2 Compose the "Sectors" selectbox using data from database
> 3. Perform the following activities after the "Save" button has been pressed:
>    3.1 Validate all input data (all fields are mandatory)
>    3.2 Store all input data to database (Name, Sectors, Agree to terms)
>    3.3 Refill the form using stored data
>    3.4 Allow the user to edit his/her own data during the session

`index.html` is a bare fragment: an intro sentence, a text input, a `select multiple` with 79
hardcoded options whose hierarchy is faked with `&nbsp;` indentation, a checkbox and a submit
button, all separated by `<br />` tags and not wrapped in a `form`.

### 1.1 Actors and assumptions

- One anonymous end user per browser session. No login, no administrator, no other roles.
- UI language stays English, as in the original.
- One submission per browser session. Saving again in the same session updates it.
- "Session" means the server-side HTTP session identified by a cookie. It survives page reloads
  and closed tabs, and ends on idle timeout (30 minutes) or when the browser clears cookies.
- Selecting a parent sector does not imply its children. Every level is independently selectable,
  as in the original list.
- There is no actual terms document. The checkbox label stays "Agree to terms".
- Sector names are the client's data and stay as given, including the three plain "Other" entries.
  The UI disambiguates them by showing the full path (for example *Manufacturing › Machinery › Other*).

Out of scope: authentication, editing sectors through the API, deleting submissions,
localisation, sharing sessions between several backend instances, admin views.

### 1.2 Deficiencies in index.html and how each is fixed (task 1)

| # | Deficiency | Fix |
|---|---|---|
| 1 | Not a document: no doctype, `html lang`, `head`, `meta charset`, `title` or `body`. The curly apostrophe in "Children’s room" has no declared encoding. | Proper HTML5 document generated by Vite with `lang="en"`, UTF-8, viewport and title. |
| 2 | No `form` element; the submit button has nothing to submit and no `action`/`method`. Pressing Save does nothing. | A `form` whose submit handler validates and calls the REST API. |
| 3 | Inputs have no `id` or `name`; "Name:", "Sectors:" and "Agree to terms" are loose text, not `label` elements, so they are not clickable and not announced by screen readers. | Every control has an `id`, a `name` and an associated `label`; hints and errors are linked with `aria-describedby`. |
| 4 | Nothing is mandatory: no `required`, no length limit, no validation at all. | Client- and server-side validation with the same rules; `maxLength` 255; `aria-required` and `aria-invalid`. |
| 5 | The 79 sectors are hardcoded in markup. | Sectors live in the database and are loaded from `GET /api/sectors`. |
| 6 | The hierarchy is faked with `&nbsp;` indentation: presentation inside content, invisible to assistive technology. | Real parent/child data; options are indented by level with a CSS class, never with spaces. |
| 7 | `size="5"` shows 5 of 79 rows. | Larger listbox (about 12 rows). |
| 8 | Multi-select with no hint that Ctrl/Cmd-click is needed. | Visible hint; the selected sectors are listed under the box with their full path. |
| 9 | Dirty option labels: trailing spaces ("Fish & fish products "), undecoded entities, inconsistent disambiguation ("Other (Furniture)" vs three plain "Other"). | Names are trimmed and decoded when the seed migration is generated; ambiguity is resolved by showing the path. |
| 10 | The checkbox has no `id`, `name`, `value` or label association, and agreement is not enforced. | Labelled, named checkbox validated as "must be true". |
| 11 | Layout via `<br />` and XHTML self-closing syntax. | Semantic structure and a small stylesheet. |
| 12 | No persistence, no feedback after saving, no way to edit later. | REST backend, success and error messages, edit mode bound to the session. |

### 1.3 Sectors (task 2)

**2.1 Sectors in the database**

- The `sector` table is seeded by the Flyway migration `V2__seed_sectors.sql`, which is generated
  mechanically from `index.html` so that the 79 rows are transcribed without error.
- Primary keys are the original `option value` attributes (1, 19, 342, ...). They are business
  identifiers and are not generated by the database.
- `parent_id` is derived from indentation depth: 0 `&nbsp;` is a root, 4 is level 1, 8 is level 2,
  12 is level 3. Result: 3 roots, 19 sectors at level 1, 47 at level 2, 10 at level 3.
- `sort_order` is the original position 1 to 79, so ordering by it reproduces the original
  depth-first list.
- Names are trimmed and `&amp;` is decoded. The typographic apostrophe in "Children’s room" is kept.
- The SQL is valid for both PostgreSQL and H2 in PostgreSQL mode.

**2.2 Select box built from the database**

- `GET /api/sectors` returns the tree: an array of roots, each with `id`, `name` and `children`,
  ordered by `sort_order` at every level. The sector list is read from the database once per
  application start and served from an in-memory cache afterwards; it only changes through a
  migration, so nothing needs to be evicted.
- The frontend flattens the tree into options carrying a `level` and a `path`.
- Options are indented by level with CSS. While sectors load the select is disabled; if the request
  fails an error with a retry action is shown.
- The currently selected sectors are listed under the box with their full paths.

### 1.4 Saving (task 3)

**3.1 Validate all input data**

The same rules apply on the client and on the server:

| Field | Rule | Message |
|---|---|---|
| `name` | required after trimming, at most 255 characters | "Name is required" / "Name must be at most 255 characters" |
| `sectorIds` | at least one; every id must exist; duplicates are ignored; no null elements | "Select at least one sector" / "Unknown sector ids: [...]" |
| `agreedToTerms` | must be present and `true` | "You must agree to the terms" |

- The client validates first and does not send an invalid form. Errors appear next to the field,
  the first invalid field receives focus and an error summary with `role="alert"` is announced.
- The server validates independently with Bean Validation and answers `400` with an
  `application/problem+json` body (RFC 9457) whose `errors` member lists the invalid fields as
  `{field, message}` pairs. All invalid fields are reported at once. Sector ids that do not exist
  are rejected by the service with `400` and the unknown ids listed in `detail`; the form itself
  can only send ids it received from the API, so this guards hand-made requests.
- Server-side messages are shown next to the fields, so the UI stays correct even if client
  validation is bypassed. Malformed JSON yields `400` without an `errors` member.

**3.2 Store all input data**

- `POST /api/submissions` creates a `submission` row with the trimmed `name`, `agreed_to_terms`,
  `created_at`, `updated_at`, and one `submission_sector` row per selected sector.
- The response is `201` with the stored representation: `id`, `name`, `sectorIds` in display
  order, `agreedToTerms`, `createdAt`, `updatedAt`.
- The submission id is stored in the HTTP session. A second `POST` in the same session returns
  `409`, telling the client to update the existing submission instead.

**3.3 Refill the form using stored data**

- After a successful save the form is repopulated from the response body, not from local state,
  so the user sees exactly what was stored (for example the trimmed name).
- On page load the client calls `GET /api/submissions/current`. On `200` the form is prefilled and
  enters edit mode; on `404` it starts empty in create mode.
- A success message states that the data was saved and can be edited during this session.

**3.4 Edit own data during the session**

- `PUT /api/submissions/{id}` replaces name, sectors and agreement. It is allowed only if the id
  stored in the session equals `{id}`; otherwise `403`, whether or not the id exists, so ids cannot
  be probed. `GET /api/submissions/{id}` follows the same rule.
- If the session has expired, `current` returns `404` and the form starts fresh. If a `PUT` gets
  `403` or `404`, the client explains that the session has expired and switches to create mode,
  keeping the typed values.
- A different browser or a private window never sees another session's data.
- Session cookie: `HttpOnly`, `SameSite=Lax`, 30-minute idle timeout. Sessions are held in memory,
  so a backend restart ends them; Spring Session JDBC would be the extension path.

### 1.5 API summary

| Method | Path | Success | Errors |
|---|---|---|---|
| `GET` | `/api/sectors` | `200` tree | |
| `POST` | `/api/submissions` | `201` | `400` validation, `409` session already owns one |
| `GET` | `/api/submissions/current` | `200` | `404` nothing saved in this session |
| `GET` | `/api/submissions/{id}` | `200` | `403` not owner, `404` |
| `PUT` | `/api/submissions/{id}` | `200` | `400`, `403`, `404` |

All errors are RFC 9457 problem details. OpenAPI documentation is served at `/swagger-ui.html`
and `/v3/api-docs`.

## 2. Data model

```
sector 1 ──── * sector            (parent_id, self-reference, null for roots)
submission * ──── * sector        (via submission_sector)
```

**`sector`** — reference data, seeded by Flyway, never edited through the API

| Column | Type | Constraints |
|---|---|---|
| `id` | `bigint` | PK, not generated (the original option value) |
| `name` | `varchar(255)` | not null |
| `parent_id` | `bigint` | FK → `sector.id`, null for roots |
| `sort_order` | `int` | not null, unique |
| | | unique `(parent_id, name)`, index on `parent_id` |

**`submission`** — one saved form

| Column | Type | Constraints |
|---|---|---|
| `id` | `bigint` | PK, identity |
| `name` | `varchar(255)` | not null, check not blank |
| `agreed_to_terms` | `boolean` | not null, check `= true` |
| `created_at` | `timestamp with time zone` | not null |
| `updated_at` | `timestamp with time zone` | not null |

**`submission_sector`** — the selected sectors of a submission

| Column | Type | Constraints |
|---|---|---|
| `submission_id` | `bigint` | FK → `submission.id`, on delete cascade |
| `sector_id` | `bigint` | FK → `sector.id` |
| | | PK `(submission_id, sector_id)`, index on `sector_id` |

Ownership is deliberately not a column: it lives in the HTTP session, so the database holds only
form data. "At least one sector" cannot be a simple constraint and is enforced in the service layer.

**Migrations** live in `backend/src/main/resources/db/migration` and run automatically on start:

| File | Content |
|---|---|
| `V1__create_schema.sql` | the three tables above with their constraints and indexes |
| `V2__seed_sectors.sql` | the 79 sectors; generated, do not edit by hand |

The seed is produced from `docs/original/index.html` by `backend/tools/generate-sector-seed.mjs`
(option value → `id`, `&nbsp;` depth → `parent_id`, position → `sort_order`, labels trimmed and
decoded). Regenerate it with:

```bash
cd backend
node tools/generate-sector-seed.mjs
```

The SQL uses only syntax shared by PostgreSQL and H2, so the same files run in production and in
the tests.

## 4. Running the application

### 4.1 What you need

- Docker with the Compose plugin (Docker Desktop on Windows and macOS; on Windows it requires WSL 2).
- JDK 25. If another Java 17+ is installed instead, Gradle downloads JDK 25 automatically.
- Node.js 22 or newer (for the frontend).

Gradle and PostgreSQL do not need to be installed: the repository ships the Gradle wrapper and
PostgreSQL runs in Docker.

All commands are run from the `sectors-form` folder. In PowerShell use `.\gradlew` instead of
`./gradlew`.

### 4.2 Start the database

```bash
docker compose up -d db
```

PostgreSQL 17 listens on `localhost:5432`; database, user and password are all `sectors`. Data is
kept in the `db-data` volume.

### 4.3 Start the backend

```bash
cd backend
./gradlew bootRun
```

The backend runs on `http://localhost:8080`, applies the Flyway migrations on start and serves:

| URL | Content |
|---|---|
| `http://localhost:8080/swagger-ui.html` | Swagger UI to browse and try the API |
| `http://localhost:8080/v3/api-docs` | OpenAPI document |
| `http://localhost:8080/api/sectors` | the sector tree |
| `http://localhost:8080/api/submissions` | saving and editing submissions (see the API summary above) |

Connection settings can be overridden with environment variables:

| Variable | Default |
|---|---|
| `DB_URL` | `jdbc:postgresql://localhost:5432/sectors` |
| `DB_USER` | `sectors` |
| `DB_PASSWORD` | `sectors` |
| `SERVER_PORT` | `8080` |

The Compose database accepts `DB_PORT` (host port, default `5432`) and `POSTGRES_PASSWORD`
(default `sectors`).

### 4.4 Start the frontend

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The dev server proxies `/api` to the backend on port 8080, so the form
and the API share one origin and the session cookie needs no extra configuration.

### 4.5 Stop

Stop the frontend and the backend with `Ctrl+C`, then:

```bash
docker compose down        # keeps the stored data
docker compose down -v     # also deletes the stored data
```

### 4.6 Build and test the backend

```bash
cd backend
./gradlew spotlessApply build
```

Runs formatting, compilation, the tests against in-memory H2 (no Docker needed) and the JaCoCo
coverage gates. Reports: `backend/build/reports/tests/test/index.html` and
`backend/build/reports/jacoco/test/html/index.html`.

### 4.7 Build and test the frontend

```bash
cd frontend
npm run build      # type-check and production build into frontend/dist
npm test           # unit tests (Vitest)
npm run lint       # oxlint
```

End-to-end tests and the full Docker Compose setup follow in steps 6 to 8.
